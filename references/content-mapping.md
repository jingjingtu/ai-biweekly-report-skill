## B 端验证叙事

当 `narrativeMode` 为 `b-end-validation` 时，使用 [B 端历史汇报内容标准](b-end-content-standard.md) 而非通用进展清单：

| 叙事位置 | 核心问题 | 推荐模块 |
|---|---|---|
| 本期变化 | 能力从什么状态推进到什么状态 | 判断标题 + 阶段标签 |
| 问题发现 | 哪次实验、哪个环境暴露了什么 | 问题主卡 + 真实截图 |
| 根因判断 | 是规则缺失、平台差异还是架构边界 | 症状/根因对照 |
| 规则化解决 | 新增了什么可执行契约或门禁 | 规则卡 + 配置/目录/Prompt 证据 |
| 复验结果 | 在哪些组件、页面或平台通过 | 验证矩阵 + Before/After |
| 能力沉淀 | 下次可以直接复用什么 | 资产分层或调用入口 |
| 下一步 | 哪个边界仍未闭环 | 2–3 张可验收动作卡 |

普通 `progress[]` 可以作为辅助材料，但不能替代问题、规则和复验之间的因果关系。

## 内容选择模块

| 内容特征 | 使用模块 | 写作重点 |
|---|---|---|
| 目标与方法论 | 主目标框 + 能力路径 | 为什么做、最终形成什么能力 |
| 2–4 个目标值或实际值 | 2–4 列指标带 | 明确区分目标、实际和待采集基线 |
| 3 个阶段 | 时间轴 + 三阶段卡 | 当前/下一步/远期的门槛关系 |
| 2–4 项本期推进 | 状态卡 | 动作、交付物、证据、状态 |
| 有界面或文件证据 | 截图证据区 | 图注写证明了什么 |
| 有前后变化 | Before/After 对照 | 强调设计判断与变化 |
| 有复用链路 | 流程带 | 输入、生成、校验、输出、迭代 |
| 有风险或未解决事项 | 问题与取舍表 | 不回避代价，给出处理边界 |
| 下期计划 | 3 张 Next 卡 | 动作必须带可验收交付物 |
| 需要会议拍板 | 决策/诉求主卡 | 写清选项、影响和期望决策时间 |

## 视觉样例原型映射

用户指定视觉样例时，先读取 [视觉样例审查](sample-standard.md)，再将业务内容映射到一个主原型：

| 主原型 | 优先叙事 | 主要证据 |
|---|---|---|
| `strategy-progress` | 目标 → 工作流变化 → 三步路径 → 组合进度 | 目标口径、流程对照、分组清单 |
| `capability-roadmap` | 能力组合 → 三阶段路线 → 内测闭环 → 下周期 | 版本门槛、测试记录、训练产出 |
| `capability-system` | 生产方式升级 → 能力分层 → 建设路径 → 案例 | 系统框架、进度盘点、真实案例 |
| `portfolio-operations` | 专项命题 → 工作流演进 → Skill 组合 → 业务覆盖 | 复用场景、调用对象、能力状态 |
| `b-end-transformation` | Before/After → 三阶段复用 → 覆盖指标 → 量化案例 | 页面截图、平台覆盖、同口径耗时 |
| `gallery-case` | 单 Skill 价值 → 传统/Skill 对比 → 成果画廊 | 输入约束、生成产物、代表案例 |

只选择一个主原型。其他原型的模块可作为补充，但不能拼出两套互相竞争的封面、指标系统或进度结构。

## 双周会默认叙事

1. **目标不变**：一句话重申北极星，不展开全年背景。
2. **本期变化**：说明从上一周期推进到了什么状态。
3. **关键证据**：每项必须能指向文件、组件、页面、报告或真实项目；数量由材料决定。
4. **当前缺口**：指出尚未验证的范围和数据。
5. **下一周期**：给出可验收动作，并尽量标注负责人和期限。
6. **需要推动的事**：存在决策或资源诉求时单独呈现，不埋在进展卡里。

## 三页浓缩版叙事

当用户要求“浓缩一下”“只要 3 页 PPT”“空白处生成 3 页版本”时，优先使用下面的三页逻辑，而不是把完整双周结构塞进三页。

1. **本期判断**：用一句话说明本期真正变化，不写流水账。页面可以包含 `一句话结论 + 3 个关键数字/状态 + 一条路径`。
2. **做了什么 / 体验节奏**：把动作按用户理解路径重组，例如 `入口可感知 → 操作有仪式 → 等待有反馈 → 结果可理解`，不要只按任务清单排列。
3. **验证入口 / 反馈闭环**：把扫码、试用、反馈和下一步处理讲清楚。观众需要做的事用大卡片突出；团队收到反馈后的处理动作降级为流程条或说明带。

三页版必须保留信息密度，但每页只讲一个判断。若用户要求更有设计感，可以用更强的视觉节奏和分区，但不能牺牲标题可读性、卡片间距和语义层级。

## 语义层级规则

同一页面中，必须先判断每组信息属于哪一层：

| 层级 | 典型内容 | 推荐表现 |
|---|---|---|
| 观众需要记住的结论 | 本期判断、关键变化、阶段结果 | 大标题、主卡片、核心数字 |
| 需要当场推动的决定 | 方案选择、优先级、资源诉求 | 决策主卡、选项对照、明确 Ask |
| 观众需要验证或反馈的问题 | 入口是否清楚、等待是否舒适、结果是否看懂 | 2–4 张重点卡片 |
| 团队内部后续动作 | 整理反馈、回归验证、排期提审 | 流程条、低权重说明带、Next 标注 |
| 背景或辅助证据 | README、截图、版本号、路径说明 | 小标签、图注、弱描边卡片 |

不要把不同层级内容放进同一个等权网格。尤其是“反馈问题”和“反馈后的处理流程”必须分开表现，否则观众会误以为所有卡片都是同一任务。

## 状态词典

- `DONE / 已完成`：交付物存在，且已检查。
- `VERIFY / 验证中`：已生成或已迁移，但仍需真实场景验证。
- `BLOCKED / 受阻`：存在明确外部依赖，必须写依赖对象。
- `NEXT / 下一步`：尚未开始或下一周期计划。
- `BASELINE / 待采集`：需要补充时长、复用、返工或覆盖数据。

## 数据纪律

- 计划数字保留，并标注 `YEAR-END TARGET`。
- 实际数字必须能追溯到用户材料或可验证文件。
- 不知道完成率时，不从任务数量推算百分比。
- 可以展示“3 个模块”“2 份真实页面”“9 张图片”等已验证计数。
- 效率提升没有前后基线时，写“已建立采集口径”，不写“提效 XX%”。
- 实际指标必须带统计截止日期和来源；计划值必须标记 `TARGET`。

## Figma 内容块标记

所有重复卡片必须在 HTML 中使用独立、唯一、可读的中文名称：

```html
<article class="card" data-figma-block="组件库迁移">...</article>
<div class="proof" data-figma-block="图片嵌入">...</div>
```

不要把整行卡片只标成一个内容块，也不要把背景和文字分别放进不同内容块。
