# B 端历史汇报内容标准

## 定位与优先级

本文件来自用户本人历史 B 端汇报，是 **内容逻辑、判断方式和证据组织的一手标准**。当任务涉及 B 端设计系统、组件库、页面模式、Skill、平台适配或生成能力验证时，优先使用本文件组织叙事。

[视觉样例基准](sample-standard.md) 中的旧样例来自其他团队，只提供配色、版式和视觉节奏参考。两类样例冲突时按以下顺序处理：

1. 当前任务的真实材料决定事实。
2. 本文件决定 B 端汇报的内容顺序与判断逻辑。
3. 视觉样例决定画布、卡片、色彩和构图方式。

不能为了匹配视觉样例打乱问题推演，也不能把历史汇报中的项目名、数字、截图或结论直接移植到新报告。

## 五角色审查结论

- **架构师**：内容标准与视觉标准必须解耦；B 端叙事以验证闭环为主，视觉原型只负责承载。组件、页面、平台和验收规则应表现为不同层级，不能压成一个“Skill 进度”。
- **设计师**：历史汇报依赖大量真实截图、结构图、代码/Prompt、对比和结论条。信息密度高，但每章都有大标题判断和绿色关键短语作为阅读锚点。
- **产品经理**：汇报价值在于解释“本轮学到了什么、为什么改变方法、沉淀了什么复用能力”，而不是报任务完成率。下一步由当前验证缺口自然推出。
- **研发**：经验只有写成组件规则、配置、契约、Golden Sample、Validation Profile 或可复用 Skill 才算能力沉淀。口头经验和单张成功页面不能标记为可复用。
- **测试**：每一轮验证必须保留范围、前置条件、结果、失败点、修正规则和复验状态。跨平台可用不能由一次成功推断，效率数据必须使用同口径基线。

## B 端默认叙事

设置 `narrativeMode: b-end-validation` 时，按下面的推理链选择章节。材料缺少某一环时标记待确认，不用空卡片补齐。

1. **本期变化**：用“从 X 推进到 Y”说明能力状态变化，而不是重复长期目标。
2. **问题发现**：展示本轮实验暴露的具体问题、出现环境和真实证据。
3. **根因判断**：解释问题为什么发生；区分表面症状、规则缺失、平台差异和架构边界。
4. **规则化解决**：把判断写成组件规则、页面配置、契约、样板、验证门禁或 Skill 结构。
5. **复验结果**：说明在哪些组件、页面、平台或项目中验证，哪些通过，哪些仍有边界。
6. **能力沉淀**：回答这轮留下了什么可复用资产，以及下一次如何直接调用。
7. **下一轮验证**：从未闭环的问题推出动作、交付物、负责人、期限和验收口径。

目标与长期路径只需在首章简短对齐。除非目标发生变化，不要在后续章节重复讲愿景。

## 标题与判断语言

优先使用能表达状态变化、因果或取舍的标题：

- `从“能生成”推进到“能复用”`
- `问题不只是平台差异，而是组件调用与验收尚未闭环`
- `一次实验的价值，是把盲点变成可执行验收规则`
- `复用的不是一张页面，而是结构、组件与生成规则`
- `目标没有改变，架构选择随阶段变化`
- `下一轮只验证三件事：差异、规则和团队复用`

这些句式是写作结构，不是固定文案。每个判断后必须紧跟证据或规则变化，不能只做绿色口号。

避免：

- 用“完成了 A、B、C”代替本期结论。
- 把工具调用、文件创建或截图数量直接写成业务价值。
- 把一次生成成功写成“稳定复用”。
- 把所有问题归因于 Prompt；先检查组件规则、平台差异、数据契约和验收门禁。
- 先写下期计划，再倒推一个与证据无关的问题。

## 验证闭环对象

### problemFindings[]

记录问题现场，而不是抽象评价：场景、症状、证据、影响和初步判断。示例：同一 Slot 在不同平台被识别但未被正确调用。

### ruleChanges[]

记录把经验变成什么可执行规则：组件选择规则、字段配置、平台适配层、Golden Sample Contract、Validation Profile、生成后检查或错误恢复。

### validationRounds[]

每轮包含：验证范围、假设、结果、失败点、修正规则、复验状态和证据。失败不是负面附录，而是下一条规则的来源。

### reusableAssets[]

只收录可再次调用的资产，例如标准组件、组件示例、页面模式、主题/平台配置、验收规则、Golden Sample、Skill、仓库入口。单张截图和一次性成稿不算复用资产。

## 能力成熟度门槛

| 阶段 | 通过门槛 | 不能据此升级 |
|---|---|---|
| `GENERATE` 能生成 | 在限定输入下生成可检查结果 | 有一张成功截图 |
| `USABLE` 单点可用 | 真实场景完成且问题可定位 | Demo 可运行 |
| `STABLE` 稳定可用 | 同类输入重复验证，验收规则可执行 | 任务数量增加 |
| `PORTABLE` 可迁移 | 平台差异被隔离，通用规则保持一致 | 复制一份 Skill |
| `REUSABLE` 可规模复用 | 新组件/页面能直接调用沉淀资产，返工与边界可追踪 | 计划覆盖多个团队 |

进度百分比必须有可数的验收项和分母；否则显示阶段与下一门槛。

## 证据编排

一个关键判断优先用 2–4 类互补证据：

- 真实页面或组件截图：证明输出状态。
- Before/After 或跨平台并排：证明差异与修复。
- Prompt、配置、规则或目录结构：证明方法已经可执行。
- 验收记录、错误日志或回归结果：证明结论不是肉眼判断。
- 仓库、Skill 或 Golden Sample 入口：证明资产可以再次调用。

截图下方的结论条要回答“因此沉淀了什么”，不要重复描述画面。

## 收束规则

结尾优先使用“两条收获 + 三项下期动作”或“当前门槛 + 下一验证入口”：

- 收获写机制：例如平台差异隔离、验收契约形成、组件族复用路径建立。
- 下期动作必须对应尚未闭环的边界，不能另起一组无关任务。
- 需要团队协作时，说明要对方提供什么样本、在哪个入口验证、何时反馈。

## 一致性验收

- 已标明 `narrativeMode: b-end-validation`，并记录采用的历史内容样例。
- 章节顺序能形成“变化—问题—根因—规则—复验—沉淀—下一步”闭环。
- 每个“可复用、稳定、跨平台、提效”结论都有对应门槛和证据。
- 失败与差异已经转化为规则或下一验证动作，没有被隐藏为“持续优化”。
- 组件、页面、平台和 Skill 层级清楚，没有混为同一级进度项。
- 视觉样例没有改写内容逻辑，历史项目事实没有进入新报告。
